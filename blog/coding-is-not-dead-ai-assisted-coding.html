Coding Is Not Dead. It Has Evolved Into AI-Assisted Coding.

The future of software engineering isn't about writing every line of code yourself. It's about knowing what to build, directing AI to build it, understanding what it produces, and having the engineering judgement to make it production-ready.

There's a lot of discussion happening in the software engineering community right now.

Some people believe coding is dead. Others believe software engineers will soon be replaced by AI. You'll even find developers arguing that learning programming languages is becoming pointless, because AI can generate entire applications in minutes.

I think both sides are missing something important.

Coding is not dead. The way we write code is changing.

We're moving from traditional software development towards AI-assisted software development. Instead of spending most of your time manually writing code, you're increasingly spending it on understanding problems, planning solutions, directing AI agents, reviewing implementations, testing outcomes and making architectural decisions.

01 · The workflow

Coding is not dead. The engineering workflow has changed.

Think about how software development traditionally worked.

You receive a requirement, understand it, design a solution, write code, debug errors, write tests, review the implementation and eventually ship it. Most of your time goes into translating your understanding into code.

With AI-assisted coding, that workflow changes. You still need to understand the requirement, but now you can ask AI to analyse it, propose an implementation, generate code, create tests, identify potential problems and even execute several development tasks for you.

Your responsibility shifts towards directing and validating the work.

Let me give you a simple example. Suppose you need to build a dashboard with several charts, filters, tables and API integrations. Here's how the two approaches compare:

The traditional way
you type almost everything
  1. Understand the requirements.
  2. Create the component structure.
  3. Design the state management approach.
  4. Write the API integration.
  5. Implement the charts.
  6. Handle loading and error states.
  7. Write tests.
  8. Fix bugs.
  9. Refactor the implementation.
The AI-assisted way
you direct and validate
  1. Ask AI to analyse the requirements.
  2. Ask it to propose the component architecture.
  3. Discuss state management and API integration strategies.
  4. Generate the initial implementation.
  5. Ask it to write tests.
  6. Run the application and inspect the output.
  7. Ask it to investigate errors.
  8. Review the generated code and improve it.

You're still engineering the solution. You're simply delegating more of the implementation work.

The difference is that your productivity is no longer limited by how quickly you can type code.

It's increasingly limited by how well you understand the problem, and how effectively you can guide AI.

02 · Experience matters more

Senior engineers have an enormous advantage

I believe senior engineers are among the biggest beneficiaries of AI-assisted coding.

Why? Because AI is extremely good at generating code, but generating code is only one part of building reliable software. An experienced engineer already understands:

Why certain architectural decisions are made.
When an abstraction is necessary, and when it isn't.
How frontend applications should scale.
How APIs should be designed.
How performance bottlenecks develop.
How to identify security vulnerabilities.
How to recognise poor coding practices.
How to investigate complicated production issues.
How to evaluate technical trade-offs.

AI can generate a React component in seconds. But then the real questions start:

AI generated <UserCard />in a few seconds
  • Should this component have its own state?
  • Should it use a shared state management solution?
  • Should the logic move into a custom hook?
  • Should it be server-rendered?
  • How will it behave when the application grows?
These questions need engineering judgement, not faster typing.

An experienced engineer can ask AI much better questions, because they understand the consequences of different implementation choices.

Imagine two developers working on the same feature. Developer A has ten years of engineering experience. Developer B has one year. Both have access to exactly the same AI tools.

A
Developer A
10 years of experience + AI
  • Explains the existing architecture.
  • Identifies the right boundaries for implementation.
  • Asks AI to investigate potential side effects.
  • Recognises when the generated solution is unnecessarily complicated.
  • Evaluates performance and maintainability.
  • Spots edge cases that AI might have overlooked.
VS
B
Developer B
1 year of experience + AI
  • Generates a working implementation.
  • Struggles to recognise architectural problems.
  • Can miss the subtle bugs hiding in generated code.
Same tools, very different outcomes. The gap is judgement, not access.

This is why I don't believe AI makes engineering experience irrelevant.

The amplifier

AI amplifies the capabilities of an engineer. The more engineering judgement you have, the more effectively you can use that amplification.

If you're a senior engineer, take advantage of this opportunity rather than worrying that AI will make your experience irrelevant. You can now experiment with more ideas, investigate more technical alternatives and finish implementation-heavy tasks much faster.

Your experience becomes more valuable when you combine it with these capabilities.

03 · If you're starting out

Junior engineers: don't start directly with vibe coding

This is probably the most important advice I'd give anyone starting their software engineering career.

AI makes it incredibly easy to generate applications without understanding how they work. You can describe an app, ask an AI coding tool to build it, and watch hundreds of lines of code appear in front of you.

That's exciting. But it can also create a dangerous illusion of competence.

You might build a working app without understanding:

JavaScript fundamentals Asynchronous programming Variables, functions and closures Data structures and algorithms HTTP requests and responses Browser rendering React lifecycle and rendering State management Error handling Testing Application architecture

The problem shows up the moment something breaks. You might have a working application, but you won't know how to investigate the problem on your own.

You ask AI to fix the issue, and it introduces three more problems while trying to solve the first one.

1 bug “AI, fix this”

That's why I recommend a different learning path:

Fundamentals AI-assisted development Vibe coding

I'd divide your learning journey into three stages.

Stage 1
Understand the fundamentals
  • Understand the language you're working with.
  • Learn how the browser and runtime work.
  • Understand functions, objects, promises and async code.
  • Learn how APIs work.
  • Understand frameworks instead of memorising syntax.
  • Learn debugging and testing.
  • Build small applications yourself.

You don't need to memorise every method. You need to understand the concepts underneath.

Stage 2
Become an AI-assisted developer
  • Ask AI to explain unfamiliar code.
  • Generate implementations and study them.
  • Ask it to compare different approaches.
  • Use it to identify bugs.
  • Generate unit tests.
  • Ask it to review your code.
  • Ask why a particular implementation works.

Don't blindly accept the generated code. Make sure you understand it.

Stage 3
Embrace vibe coding and agents
  • Build complete features using AI.
  • Generate application scaffolding.
  • Ask agents to investigate and implement tasks.
  • Build side projects quickly.
  • Experiment with new frameworks.
  • Automate repetitive engineering work.

You're no longer implementing everything by hand. You're directing the process and reviewing its output.

The sequence matters. A developer who understands the fundamentals and uses AI is far more capable than someone who only knows how to generate code through prompts.

04 · Let's get practical

Five ways to use AI to the maximum while coding

There are many ways to bring AI into your day-to-day development, but if you asked me where to start, I'd prioritise these five workflows.

01

Use AI before writing any code

Most developers open their IDE and immediately start implementing the requirement. I'd change that habit.

Before you write any code, spend some time discussing the problem with AI. Give it the requirement and ask it to identify:

missing requirements functional expectations edge cases technical dependencies implementation approaches potential risks testing requirements

For example, instead of immediately asking AI to build a user management module, start with this:

Prompt

Analyse this user management requirement. Don't write any code yet. Identify the functional requirements, edge cases, API dependencies, state management requirements and possible architectural concerns. Then suggest an implementation plan.

Then challenge its recommendations:

  • Is this architecture unnecessarily complicated?
  • What happens when the API fails?
  • How should permissions be handled?
  • How will this work with 100,000 users?
  • What would you change if multiple teams had to use this?
You're using AI as a technical thinking partner. This alone can save you a significant amount of rework.
02

Delegate implementation to AI

Once you have an implementation plan, let AI handle as much of the repetitive implementation as possible. For example:

React components TypeScript interfaces API clients reusable hooks forms and validation unit tests mock data documentation refactoring repetitive code

Just don't give vague instructions. Compare these two:

Instead ofCreate a reusable table component.
TryCreate a reusable React and TypeScript table component. It should support sorting, pagination, column configuration, loading states, empty states and row selection. Follow the existing component conventions in this repository. Keep the implementation modular and include unit tests.

The more context and constraints you give, the more useful the result becomes.

And don't ask an agent to modify your entire application when you only need one feature. Give it a clearly defined scope.
03

Use AI as your code reviewer

This is one of the most underrated uses of AI. Most of us use it to generate code and completely forget to use it to evaluate our own implementation.

Before you merge a pull request, ask AI to review the changes and look for:

  • Logical errors.
  • Security vulnerabilities.
  • Performance problems.
  • Unnecessary complexity.
  • Memory leaks.
  • Accessibility issues.
  • Incorrect error handling.
  • Missing test cases.
  • Breaking changes.

Here's a review prompt I find useful:

Review prompt

Review this implementation as a senior software engineer. Focus on correctness, maintainability, performance, security and edge cases. Don't simply approve the implementation. Identify concrete issues and explain why they matter. Separate critical problems from optional improvements.

You can also ask it to check the implementation against your original requirements.

AI reviews don't replace human code reviews, security checks or automated testing. Treat them as one more layer of quality control.
04

Use AI for debugging and root cause analysis

Debugging can eat an enormous amount of engineering time. A problem that looks simple might involve multiple components, API responses, state transitions and asynchronous operations.

Instead of trying random fixes again and again, use AI to investigate systematically. Give it:

The error message
Relevant source code
Steps to reproduce
Expected behaviour
Actual behaviour
Relevant logs
Recent code changes

Then ask it to identify possible root causes and rank them by likelihood. Here's the difference a good prompt makes:

Instead ofFix this bug.
TryInvestigate this production issue. The component renders correctly initially, but after changing filters, the table displays stale data. Analyse the state transitions and asynchronous API calls. Identify possible race conditions and suggest a minimal fix. Don't modify code until you explain the root cause.
The goal is to solve the actual problem, not hide its symptoms.
05

Use AI to automate repetitive engineering work

Think about everything you repeat every week. You might keep:

creating similar components writing similar tests updating TypeScript interfaces generating API docs creating mock data updating config files investigating build failures writing release notes generating migration scripts reviewing similar pull requests

A lot of this can be sped up or partly automated. You can even create reusable, project-specific instructions so AI understands your coding standards and repository conventions. Something like this:

project-instructions.md
  1. # How we work in this repo
  2. - Preferred folder structure
  3. - Component naming conventions
  4. - TypeScript standards
  5. - Testing frameworks
  6. - Error handling patterns
  7. - Styling conventions
  8. - Architectural boundaries
  9. - Commands to run before submitting changes

This saves you from explaining the same things over and over.

Over time, you're building an AI-assisted engineering environment that's tailored to your project.
05 · Pick the right brain

06 · Beyond chat

Agentic AI: move beyond asking questions

This is where AI-assisted development becomes really powerful.

Question and answer
You askAI writes codeYou copy itYou test it

The traditional pattern. You drive every single step.

Agentic
You set a goalAgent works through the stepsYou review

You're effectively delegating a development task to an AI worker.

Depending on the tool and the permissions you give it, an agent can:

Explore your repository Read existing files Understand dependencies Modify source code Create new files Run terminal commands Execute tests Investigate errors Adjust its implementation Review the resulting changes

Imagine giving an agent this task:

An illustrative agent run. The agent works through the steps so you don't have to request each one.

But agentic AI needs supervision. Don't give an agent unlimited authority over important production systems. Put some guardrails in place:

Small, well-defined tasks
Version control
Separate branches
Restricted permissions
Tests and validation
Human review before merging
Approval before destructive operations

I'd recommend starting with a single agent working on a clearly scoped feature. Once you understand how it behaves, try more complex workflows. Eventually, you can use multiple agents for independent tasks:

Agent 1Investigates the backend API
Agent 2Explores the frontend architecture
Agent 3Writes the tests
Agent 4Reviews the implementation

But parallel agents bring their own problems: coordination, conflicting changes and duplicated work. More agents don't automatically mean more productivity.

Good orchestration matters more than the number of agents.

07 · Think before you build

Use AI for planning and architectural decisions

This is something I strongly recommend. Most developers think of AI mainly as a code generator, but I believe some of its greatest value comes before implementation even begins.

Imagine you're planning a new frontend application. You need to decide:

  • Which framework to use.
  • How to organise the repository.
  • How to manage state.
  • How to handle authentication.
  • How to structure API communication.
  • How to implement permissions.
  • How to manage caching.
  • How to handle errors.
  • How to organise reusable components.
  • How to test the application.

Instead of making these decisions on your own, use AI as an architectural discussion partner. Give it the context of your application:

Expected traffic Number of users Technical constraints Team size Existing infrastructure Long-term requirements

Then ask it to propose different architectures:

Prompt 1 · Propose

I am designing a large enterprise frontend application using React and TypeScript. It will have multiple modules, role-based permissions, complex forms and extensive API integrations. Compare different approaches for application architecture, state management, routing, caching and component organisation. Explain the trade-offs and recommend a maintainable solution.

Don't accept the first recommendation. Ask it to challenge its own proposal:

Prompt 2 · Challenge it

Now act as a critical software architect. Identify weaknesses in your proposed architecture. What could become difficult to maintain? What happens when the application grows significantly? Are there simpler alternatives?

Once you're happy with the direction, ask it to produce:

Architecture diagrams Technical design documents API contracts Data flow diagrams Component dependency diagrams Implementation plans Testing strategies Migration plans
One important rule: AI recommendations are hypotheses, not architectural authority. Validate them against your actual system, engineering standards and operational constraints.
08 · Learn faster

Build side projects using AI, and bring the learning into your actual work

I love this particular use of AI.

Building a side project used to take a serious investment of time. You had to design the app, build the frontend, write APIs, configure the database, handle authentication and deploy everything. AI has dramatically reduced the effort needed to experiment with ideas like these.

Why does this matter for your career? Because side projects let you experiment without the constraints of your employer's production environment.

Say you're a frontend engineer working on a large enterprise application. You might want to explore:

A new React architecture A different state management approach A modern design system An AI-powered search interface A better data visualisation library An agent that automates repetitive tasks A new testing strategy A better way to handle complex forms

Instead of spending weeks trying to sneak an experimental approach into your production app, build a small prototype on your own. Use AI to help you build it, try different implementations, measure the results and weigh up the pros and cons. Then bring the useful ideas back to your actual work.

It creates a really powerful cycle:

  1. Spot a technical opportunity.
  2. Build a small prototype using AI.
  3. Experiment with different approaches.
  4. Evaluate the results.
  5. Learn from the implementation.
  6. Bring the validated improvement into your real project, where it fits.
repeat

A couple of ground rules

Don't copy experimental code straight into production. Review security, maintainability, licensing, dependencies and your organisation's policies first.

And never put confidential company source code or data into an unapproved external AI service.

The real benefit of side projects isn't necessarily building something that becomes a business.

It's becoming a better engineer through faster experimentation.

09 · Spend wisely

How to avoid running out of AI tokens while coding

If you use AI coding tools regularly, you'll eventually hit context limits, usage limits or a surprisingly large bill. It gets frustrating, especially on large repositories. Here's what I recommend.

01
Stop repeating information

Don't keep explaining your architecture, framework and conventions. Put them in a project instruction file your tool can read, where supported.

Tech stackRepo structureKey modulesConventionsTest commandsBuild commandsArchitecture rules
02
Keep tasks small and focused

Rather than “understand my entire app and implement all the missing features”, break it down:

Analyse auth moduleLogin pageValidationAuth APITestsReview

Smaller tasks need less context and are easier to validate.

03
Use the right model for the job

Use fast models for routine implementation. Save the expensive reasoning models for complex decisions.

04
Don't keep sending the whole codebase

Share the relevant files, interfaces, error logs and context. Ask the agent to inspect specific modules, not unrelated parts of the repo.

05
Maintain project summaries

On long tasks, ask AI for a short summary now and then. It's perfect for starting a fresh session.

ObjectiveCurrent stateFiles changedDecisionsOpen issuesNext steps
06
Keep conversations lean

Long conversations pile up irrelevant context. Start a fresh session when it makes sense, using a short handover summary.

07
Ask for minimal changes

Tell AI not to refactor unrelated files or regenerate functionality that already exists.

Prompt

Make the smallest possible change to solve this issue. Preserve the existing architecture and avoid modifying unrelated components.

08
Use caching where supported

Some AI APIs and platforms support prompt caching. Stable context like project instructions may benefit, depending on the platform.

09
Avoid pointless agent loops

An agent that keeps running tests, changing code and retrying without a plan burns resources. Ask it to explain the failure and propose the next step first.

10
Stop when the task is complete

Don't keep asking AI to optimise code that's already correct, tested and maintainable. At some point, more refinement costs more than it's worth.

The goal isn't to minimise token usage at all costs.

It's to get the most useful engineering output out of every unit of AI you use.

10 · Tell the story

Use AI to create presentations that executives will remember

Here's an opportunity a lot of engineers overlook.

We technical folks tend to communicate with documents full of paragraphs, bullet points and screenshots. Executives usually don't want to read long technical explanations. They want to understand:

What problem are we solving?
Why does it matter?
What changed?
What's the business impact?
What risks remain?
What decision is needed?

AI can help you communicate technical work visually. Say you've just finished a major frontend performance improvement. Instead of 20 slides of technical detail, use AI to build a compelling visual story with before-and-after comparisons, architecture and data flow diagrams, user journeys, bottleneck visualisations, impact charts, risk matrices and a roadmap.

A performance story could look something like this:

SLIDE 1
The problem
Show the slow user experience.
SLIDE 2
The root cause
Show the technical bottleneck.
SLIDE 3
The solution
Visualise the new architecture.
SLIDE 4
The results
Compare performance before and after.
SLIDE 5
The business impact
How it helps users and the organisation.
SLIDE 6
What's next
Present the future roadmap.

You can use AI to help with the narrative, diagrams, data visualisation and slide design, using presentation generators, diagramming tools and AI-powered document apps.

The numbers must be real

The underlying numbers and claims must come from actual measurements. Don't let AI invent performance improvements or business impact.

A beautifully designed presentation with unsupported numbers is still a bad presentation.

My advice: treat every important technical presentation as a storytelling exercise. Use visuals to make complicated engineering decisions understandable to non-technical people. That's a genuinely valuable professional skill.

15 · Watch out

The biggest mistakes to avoid

AI-assisted coding is powerful, but a few mistakes can make you less productive instead of more.

  1. Blindly accepting generated code.
  2. Letting agents change large parts of a repository without supervision.
  3. Using AI without understanding the problem.
  4. Choosing complicated architectures because AI suggested them.
  5. Generating code faster than you can review it.
  6. Skipping tests because the AI says it's done.
  7. Uploading confidential company information to unapproved AI services.
  8. Assuming AI-generated security code is automatically safe.
  9. Constantly switching tools instead of learning one properly.
  10. Producing code without understanding the business requirement.

One of the biggest dangers is building an application that looks complete but is really hard to maintain. A successful implementation isn't just code that works once. It's code that is:

Correct Maintainable Secure Testable Right for the actual requirements
